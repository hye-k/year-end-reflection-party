## 제품 범위

- 8명의 프리다이빙 클럽 친구가 연말 파티 전에 쓰는 정적 사이트다. 구글 폼 대신 직접 만든 이유는 질문의 연출과 전달을 마음대로 바꾸기 위해서다.
- 구조는 단순함이 우선이다. 서버는 구글 시트에 붙은 Apps Script 하나뿐이고, 라우터와 별도 백엔드는 두지 않는다.
- 구성은 "2026 다이브 로그"(회고, 13개 질문 전부 필수)와 "2027 시즌 훈련표"(만다라, 보너스 단계, 필수 아님, 제출은 한 칸 이상)다.
- 새해 다짐과 빙고는 만다라가 대체했고, 빙고는 만들지 않기로 했다 (2026-11-14). 배경음악도 접었다 (2026-11-13).
- 회고를 모두 답해 제출해야 "클리어"에 갈 수 있다. 만다라는 건너뛸 수 있다.

## 데이터와 저장

- 허용 이름은 시트의 `names` 탭이 정한다. 사람 목록은 시트에서 바꾸고 코드나 재배포는 필요 없다. 기록은 이름으로 묶이므로 이름은 바꾸지 않고 추가/삭제만 한다.
- 서버는 이름 허용 목록, 폼 이름, 크기, 헤더/행 길이만 검사하고 완성도는 검사하지 않는다.
- 입력은 수정 0.5초 후 localStorage에, 첫 미저장 수정 20초 후 서버에 저장한다. 수정이 없으면 호출하지 않고, 실패는 다음 수정이나 저장 버튼에서만 다시 시도한다.
- 제출한 상태를 임시저장으로 남겨 두고, 다시 들어오면 복원한다. 마지막 단계는 이어서 시작한다 (완료 화면 제외).
- 탭은 첫 기록 때 헤더와 함께 만들어진다. 초기화는 탭 전체를 지운다. 헤더 없는 빈 탭은 남기지 않는다.
- **실데이터 보호**: 친구들의 답이 시트에 있다. 질문 id, 칸 수, 열 배치를 바꾸거나 탭을 초기화하려면 먼저 기존 행을 옮긴다. 사이트 재배포는 안전하다.
- Apps Script를 고치면 **같은 배포의 새 버전**으로 올린다 (URL 유지).
- localStorage 키는 모두 `ydp:v1:`로 시작한다.

## 입력 제한

- 글자 수는 사용자가 보는 글자(grapheme) 기준이고, 상수 4개를 `core/content.ts` 한 곳에서만 관리한다. 값: 짧은 답 200, 긴 답 1000, 짧은 칸 80, 긴 칸 200 (2026-11-14에 상향).
- 칸(slot)은 한 줄 입력이고, 길면 가로로 스크롤한다. 여러 줄로 바꾸지 않는다.
- 서버의 셀 상한(2000, UTF-16 단위)보다 충분히 낮게 유지한다. 이모지는 2로 센다.

## 공개 범위와 읽기

- 모든 답변을 한 번에 읽어 주는 공개 endpoint는 만들지 않는다. 사이트 번들에 Apps Script 주소가 들어 있어서, 만들면 누구나 읽을 수 있다.
- 사이트 번들에 들어가는 것은 공개된 것으로 취급한다.

## 디자인과 카피

- 픽셀아트 "수심 다이브" 게임 룩이다. 팔레트는 Lospec Apollo, 폰트는 Galmuri11 Bold(제목, 버튼, 라벨)와 Pretendard(본문)다.
- 금색 버튼 컴포넌트 하나만 쓴다. 한 단계 앞으로 가는 버튼은 영문 대문자(START, NEXT ▼, NEXT ▶, BONUS ▶, SUBMIT!), 나머지는 한국어다.
- 카피는 친근한 한국어 요체다. 화면마다 움직이는 연출은 많아야 하나(클리어의 색종이, 완료의 크레딧)이고, reduced motion을 존중한다.
- 입력에 자동 포커스를 주지 않는다 (iPad에서 뷰포트가 줄어든다). 모바일 입력은 16px 아래로 내리지 않는다 (iOS가 확대한다).
- 레이아웃: 데스크톱은 1280x760 고정 무대를 화면에 맞춰 확대/축소한다. 너비 760px 이하는 폰 레이아웃이다. 가로 태블릿은 데스크톱 레이아웃(위아래 검은 띠 허용)이고, 세로 태블릿은 대상이 아니다.
- 질문 문구와 구조는 분리한다 (`ko.json` + `QUEST_STRUCTURES`). 다국어는 준비만 했고 UI 문자열의 키 이전과 `en.json`은 하지 않았다.

## 배포와 라이선스

- 사이트는 `cd app && npm run deploy`로 `gh-pages` 브랜치에 올린다 (GitHub Pages).
- 스프라이트(Szym's SpearFishing Assets Pack)는 라이선스상 재배포가 금지라서 `assets/`와 `app/src/assets/sprites/`는 git에서 제외한다. 그래서 빌드는 이 컴퓨터에서만 된다. 배포된 사이트에는 스프라이트 PNG가 들어가는 것을 소유자가 받아들였다. 크레딧은 `content/credits.json`에 있다.
- `image.png`, `image-1.png`(빙고 참고 이미지)는 출처를 몰라서 git에서 제외한다.
- 커밋과 푸시는 사용자가 요청할 때만 한다.

## 사용 기록 (events)

- `drafts` 탭은 `이름|폼` 키로 행을 덮어쓴다 (마지막 저장만 남는다). 저장 이력용으로 바꾸지 않는다.
- 사용 기록은 별도 `events` 탭에 append-only로 쌓는다. 기존 탭(`reflection`, `mandala`, `drafts`)의 열 배치는 건드리지 않는다.
- 사건 종류: `open`, `quest_enter`, `skip`, `save`, `submit`. 만다라는 질문이 없어 `open`, `save`, `submit`만 쓴다.
- 열: `ts,name,form,event,quest,answered,chars`. `quest`는 질문 id(해당 없으면 빈칸), `answered`는 그 시점에 채운 질문 수(만다라는 채운 칸 수), `chars`는 그 시점의 총 글자 수다. 질문별 체류 시간은 연속된 `quest_enter` 사이 간격으로 계산한다.
- 시각(`ts`)은 클라이언트 기준 UTC ISO로 저장하고, KST 변환은 보여줄 때 한다.
- 기록은 보너스다. 기록 실패가 답변 저장, 제출, 화면 이동을 막으면 안 된다. 전송은 새 호출 경로 없이 기존 저장/제출 때 묶어서 보내고(탭을 닫을 때 한 번 더 시도), 일부 유실은 허용한다.
- 알려진 유실: 이름만 고르고 한 글자도 쓰지 않고 닫으면 `open`이 서버에 못 갈 수 있다. 응답이 유실된 재전송은 같은 사건을 두 줄 쌓을 수 있다 (통계에서 중복 제거).
- events 배포 전 상태의 `drafts` 탭 사본을 시트의 `drafts_bk` 탭에 백업해 뒀다 (통계용). 2026-11-13 19:57 KST에 친구들에게 사이트를 공개했고, 사본은 2026-11-14 01:45 KST(= 2026-11-13T16:45Z)의 `drafts`를 복사한 것이다. 친구마다 그 시점의 `savedAt`(마지막 저장 시각)이 있어서, events가 없는 구간(공개 후 약 6시간)의 자료로 쓸 수 있다. 사본은 지우거나 덮어쓰지 않는다.
- 기록이 없는 친구(events 배포 전에 제출)는 "기록 없음"으로 처리하고 해당 상 후보에서 뺀다.

### 통계를 읽을 때 지킬 것

- 시트의 행 순서는 시간순이 아니다 (`save`의 `ts`는 저장 시작 시각인데 응답 후에 기록된다). 항상 `ts`로 정렬해서 계산한다.
- `ts+name+event+quest`가 같은 행은 한 건으로 본다 (재전송 중복, 개발 서버 StrictMode).
- `skip`은 "넘긴 것"이지 꼭 "미룬 것"이 아니다. 훑어보는 사람도 많이 나온다.

### `skip` 기록 조건

- 질문을 떠날 때, 그 질문이 미답이고 건너뜀 목록에 아직 없으면 한 번 찍는다. 미답은 제출 검증과 같은 규칙이다 (슬롯은 모든 칸이 차야 답한 것).
- 임시저장에서 복원된 건너뜀 표시는 새로 찍지 않는다. 답했다가 지우고 다시 떠나면 다시 찍힌다.
- 시작 화면으로 돌아가기, 제출 전 "아직 안 쓴 질문" 창, 수심계로 멀리 점프할 때 지나친 질문에는 찍지 않는다.

## 시상식 통계

"미룬 사람"은 한 점수로 합치지 않고 기준별로 상을 나눈다.

**사람 단위**

| 상 | 계산 | 대상 |
|---|---|---|
| 제출 꼴찌상 | `reflection` 제출 시각 − 링크 공유 시각 (2026-11-13 19:57 KST = 10:57Z) | 전원 |
| 넘기기 장인상 | 그 사람의 `skip` 행 수 | events가 있는 친구 |
| 열자마자 미룸상 | `open`부터 처음 `chars` > 0인 사건까지의 간격 (정확도 약 20초) | events가 있는 친구 |

**질문 단위**

| 상 | 계산 |
|---|---|
| 가장 많이 넘겨진 질문 | 그 질문에서 `skip`이 찍힌 서로 다른 사람 수 |
| 가장 오래 고민한 질문 | 연속된 `quest_enter` 사이 간격의 합. 10분(초기값) 이상은 쉬는 시간으로 보고 뺀다 |

그 밖의 후보: 작업 시간, 저장왕(저장 횟수), 지우개상(글자 수 감소), 새벽/아침형, 다이브 레이스(시간별 진행 곡선).

## 결과 화면 (아직 만들지 않음)

- 흐름: 인트로 → 질문별 익명 답변 카드 맞추기 → 이름 공개 → 질문 통계 → 만다라 갤러리 → 시상식 → 엔딩. 진행자가 이끈다.
- **잠정 가정 (미확정)**: 진행자가 자기 노트북을 큰 화면에 연결해 쓴다. 그래서 새 공개 읽기 endpoint를 만들지 않고, 로컬 데이터(CSV 내보내기, git 제외 파일)를 읽는 별도 `results.html`로 만들며 배포 빌드에는 넣지 않는다.
- 통계 계산은 `core`의 순수 함수로 두고 Vitest로 검증한다.

## 미검증

- 만다라 폼의 events(`open`/`save`/`submit`)는 실제 시트에서 확인하지 않았다. reflection 쪽은 확인했다.
